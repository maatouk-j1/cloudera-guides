Use this section when an installation has failed and you cannot resolve the issue in place — the fastest route forward is usually a clean slate. Cleanup is also a prerequisite for several of the fixes in [Error Handling](/installations/cdp-7-3-2/error-handling).

<Banner type="important">
Most of what follows cannot be undone — the `rm -rvf` blocks, `dnf remove`, `userdel -r` and the iptables flush destroy data and configuration permanently. Run them only on hosts you intend to rebuild, and read each block before pasting it. Where a step offers a choice, decide which option applies to you before you run anything.
</Banner>

## Cleanup the Base cluster

Reference: [https://docs.cloudera.com/cdp-private-cloud-base/7.3.2/cdp-private-cloud-base-installation/topics/cdpdc-uninstallation.html](https://docs.cloudera.com/cdp-private-cloud-base/7.3.2/cdp-private-cloud-base-installation/topics/cdpdc-uninstallation.html)

1. **Stop all services** in Cloudera Manager.

2. **Delete the cluster.** On the Home page, click the drop-down list next to the cluster you want to delete and select **Delete**.

3. **Uninstall the Cloudera Manager Server.** Run this on the Cloudera Manager host, `cldr-mngr`, which also runs the PostgreSQL database. It stops PostgreSQL and removes the Cloudera Manager packages, but leaves the database itself on disk — step 4 decides what happens to it.

    ```text
    [root@cldr-mngr ~]# systemctl stop postgresql-17
    [root@cldr-mngr ~]# systemctl stop cloudera-scm-server cloudera-scm-agent cloudera-scm-server-db cloudera-manager-server-db
    [root@cldr-mngr ~]# dnf remove -y cloudera-manager-daemons cloudera-manager-agent cloudera-manager-server cloudera-manager-server-db
    [root@cldr-mngr ~]# systemctl daemon-reload
    ```

    The repository definition is left in place so a rebuild can reuse it. Remove it only if the rebuild will point at a different repository:

    ```text
    [root@cldr-mngr ~]# rm -rvf /etc/yum.repos.d/cloudera-manager.repo
    ```

4. **Dispose of the PostgreSQL database.** The two options below are alternatives, not a sequence — pick one.

    - **Option 1 — move the data directory aside.** The safer choice: the databases survive under a dated backup name, so you can still inspect or restore them after the rebuild. The copy keeps consuming disk until you delete it yourself.

        ```text
        [root@cldr-mngr ~]# mv -v /var/lib/pgsql/17/data/ /var/lib/pgsql/17/data_bkp_$(date +%Y%m%d)
        ```

    - **Option 2 — delete the database and remove PostgreSQL.** Deleting the data directory is irreversible; dropping the packages and the `postgres` account leaves the host with no database at all, so the rebuild has to install one.

        ```text
        [root@cldr-mngr ~]# rm -rvf /var/lib/pgsql/17/data/
        [root@cldr-mngr ~]# dnf remove -y postgresql-contrib postgresql-17-contrib postgresql-server postgresql-17-server
        [root@cldr-mngr ~]# userdel postgres
        ```

5. **Clean up Cloudera Manager, the Base master and the worker nodes.** Run this on `cldr-mngr`, `pvcbase-master` and every `pvcbase-worker`.

    ```text
    #/opt/cloudera/installer/uninstall-cloudera-manager.sh
    [root@pvcbase-master ~]# systemctl stop cloudera-scm-server cloudera-scm-agent cloudera-scm-server-db supervisord;
    [root@pvcbase-master ~]# dnf remove -y cloudera-manager-server cloudera-manager-server-db-2 cloudera-management-agent cloudera-management-daemon cloudera-manager-*; dnf clean all; systemctl daemon-reload;
    [root@pvcbase-master ~]# for u in cloudera-scm* flume hadoop hdfs hbase hive httpfs hue impala llama mapred oozie solr spark sqoop sqoop2 yarn zookeeper; do sudo kill $(ps -u $u -o pid=); done
    [root@pvcbase-master ~]# sudo umount cm_processes
    [root@pvcbase-master ~]# sudo rm -rvf /usr/share/cmf /var/lib/cloudera* /var/cache/yum/cloudera* /var/log/cloudera* /var/run/cloudera* /etc/cloudera-scm-server /opt/cloudera /etc/cloudera-scm-agent /var/lib/cloudera-scm-agent/cm_guid*
    ```

6. **Purge the data and configuration directories.** Run this on `cldr-mngr`, `pvcbase-master` and every `pvcbase-worker`.

    ```text
    [root@pvcbase-master ~]# sudo rm -rvf /tmp/kafka-logs /tmp/.scm_prepare_node.lock /var/local/kafka/data/meta.properties /hdfs/* /dfs/* /hdfs/mapred/* /hdfs/yarn/* /var/lib/had*ozon* /yarn* /hadoop* /etc/{*atlas*,*hadoop*,*ranger*,hue,impala,knox,hbase,*hive*,hbase-solr,hadoop-kms,*ozone*,oozie,*kafka*,*zeppelin*,*spark*,sqoop*,schemaregistry,*solr*,hive-hcatalog,hive-webhcat,hue,*hbase*,*kudu*,*knox*,zookeeper,*tez*,streams*, *nifi*} /tmp/kafka-logs/* /var/lib/cloudera-scm-agent/cm_guid
    ```

7. **Remove the service accounts and groups.** Run this on all hosts, and only if you are doing an end-to-end cleanup that includes Cloudera Manager and the PostgreSQL database.

    First the accounts. `userdel -r` also removes each account's home directory:

    ```text
    [root@pvcbase-master ~]# for user in hdfs httpfs sqoop kafka yarn hbase streamsrepmgr streamsmsgmgr livy kms atlas schemaregistry hue zookeeper accumulo phoenix mapred druid ranger zeppelin oozie kudu knox superset solr hive cruisecontrol impala rangerraz ozone tez dpprofiler flume nifi nifiregistry nifitoolkit spark flink rangerrms omid hadoop kraft; do userdel -r "$user" 2>/dev/null; done
    ```

    Then the groups, which have to go second — a group cannot be deleted while it is still a user's primary group:

    ```text
    [root@pvcbase-master ~]# for group in hdfs hue httpfs sqoop kafka yarn hbase streamsrepmgr streamsmsgmgr livy kms atlas schemaregistry hue zookeeper accumulo phoenix mapred druid ranger zeppelin oozie kudu knox superset solr hive cruisecontrol impala rangerraz ozone tez dpprofiler flume nifi nifiregistry nifitoolkit spark flink rangerrms omid hadoop kraft; do groupdel "$group" 2>/dev/null; done
    ```

8. **Confirm the host is back to a bare OS** — Java and Python should still be present, since they come from the OS and not from Cloudera Manager.

    ```text
    [root@pvcbase-master ~]# java -version
    [root@pvcbase-master ~]# python3 -V
    ```

## Cleanup the Data Services (ECS) cluster

Reference: [https://docs.cloudera.com/cdp-private-cloud-data-services/1.5.5/installation-ecs/topics/cdppvc-installation-ecs-uninstall-pvc.html](https://docs.cloudera.com/cdp-private-cloud-data-services/1.5.5/installation-ecs/topics/cdppvc-installation-ecs-uninstall-pvc.html)

Every block below runs on the ECS hosts — `pvcecs-master` and each `pvcecs-worker` — never on `cldr-mngr` or the Base hosts. The prompts show `pvcecs-master`; each step says which hosts it applies to.

### 1. Remove the embedded Docker registry

Run on each host in the cluster. Only the host running the embedded registry actually has the container — elsewhere these commands report `No such container: registry` and change nothing:

```text
[root@pvcecs-master ~]# /opt/cloudera/parcels/ECS/docker/docker container stop registry
[root@pvcecs-master ~]# /opt/cloudera/parcels/ECS/docker/docker container rm -v registry
[root@pvcecs-master ~]# /opt/cloudera/parcels/ECS/docker/docker image rm registry:2
```

### 2. Stop the ECS cluster in Cloudera Manager

Do this from the Cloudera Manager UI before touching RKE2 on the hosts.

### 3. Kill and uninstall RKE2, then purge its state

Run on each host. `rke2-killall.sh` usually needs two passes before every container and mount is gone. Which block you run depends on how `/docker`, `/lhdata` and `/cdwdata` are backed.

- **Option 1 — local storage.** What this deployment uses: the three paths are local directories, so nothing has to be unmounted first.

    ```text
    [root@pvcecs-master ~]# cd /opt/cloudera/parcels/ECS/bin
    [root@pvcecs-master bin]# ./rke2-killall.sh
    [root@pvcecs-master bin]# ./rke2-uninstall.sh
    [root@pvcecs-master bin]# systemctl daemon-reload
    [root@pvcecs-master bin]# rm -rvf /ecs/*
    [root@pvcecs-master bin]# rm -rvf /var/lib/docker_server/*
    [root@pvcecs-master bin]# rm -rvf /etc/docker/certs.d/ /etc/docker/*
    [root@pvcecs-master bin]# rm -rvf /var/lib/docker/*
    [root@pvcecs-master bin]# rm -rvf /etc/rancher /var/lib/rancher /var/log/rancher /var/lib/rancher/k3s/server/node-token
    [root@pvcecs-master bin]# rm -rvf /run/k3s /opt/containerd /opt/cni
    [root@pvcecs-master bin]# rm -rvf /docker/* /lhdata/* /cdwdata/* /ecs/*
    [root@pvcecs-master bin]# rm -rvf ~/.kube ~/.cache
    [root@pvcecs-master bin]# systemctl daemon-reload
    ```

- **Option 2 — NFS-backed mounts.** If any of `/docker`, `/lhdata` or `/cdwdata` is an NFS mount, unmount it before the `rm -rvf` lines — otherwise you delete data on the NFS server rather than on the host.

    ```text
    [root@pvcecs-master ~]# cd /opt/cloudera/parcels/ECS/bin
    [root@pvcecs-master bin]# ./rke2-killall.sh
    [root@pvcecs-master bin]# umount /docker /lhdata /cdwdata
    [root@pvcecs-master bin]# ./rke2-uninstall.sh
    [root@pvcecs-master bin]# systemctl daemon-reload
    [root@pvcecs-master bin]# rm -rvf /ecs/*
    [root@pvcecs-master bin]# rm -rvf /var/lib/docker_server/*
    [root@pvcecs-master bin]# rm -rvf /etc/docker/certs.d/ /etc/docker/*
    [root@pvcecs-master bin]# rm -rvf /var/lib/docker/*
    [root@pvcecs-master bin]# rm -rvf /etc/rancher /var/lib/rancher /var/log/rancher /var/lib/rancher/k3s/server/node-token
    [root@pvcecs-master bin]# rm -rvf /run/k3s /opt/containerd /opt/cni
    [root@pvcecs-master bin]# rm -rvf /docker/* /lhdata/* /cdwdata/* /ecs/*
    [root@pvcecs-master bin]# rm -rvf ~/.kube ~/.cache
    [root@pvcecs-master bin]# systemctl daemon-reload
    ```

### 4. Delete the ECS cluster in Cloudera Manager

In Cloudera Manager, navigate to **Cloudera Data Services on premises** and click the actions menu, then **Delete**.

![Cloudera Data Services cluster tile in Cloudera Manager with the three-dot actions menu open, showing Update and Delete](/images/cdp-7-3-2/cleanup/ecs-cluster-actions-menu-delete.png)

The Delete Cluster wizard appears; click **Delete**.

![Delete Cluster dialog asking to confirm deletion of the containerized cluster, with Cancel and a red Delete button](/images/cdp-7-3-2/cleanup/ecs-delete-cluster-dialog.png)

### 5. Reset iptables on each host

RKE2 and its CNI leave a dense set of chains behind. This resets every table's built-in chains to `ACCEPT`, then flushes (`-F`) and deletes (`-X`) everything else.

```bash
echo "Reset iptables to ACCEPT all, then flush and delete all other chains";
declare -A chains=( [filter]=INPUT:FORWARD:OUTPUT [raw]=PREROUTING:OUTPUT
[mangle]=PREROUTING:INPUT:FORWARD:OUTPUT:POSTROUTING [security]=INPUT:FORWARD:OUTPUT
[nat]=PREROUTING:INPUT:OUTPUT:POSTROUTING );
for table in "${!chains[@]}";
      do
      echo "${chains[$table]}" | tr : $"\n" | while IFS= read -r;
      do
      sudo iptables -t "$table" -P "$REPLY" ACCEPT
      done
      sudo iptables -t "$table" -F
      sudo iptables -t "$table" -X
done
iptables -F; iptables -L
rm -rvf /etc/rancher /var/lib/rancher /var/log/rancher
```

### 6. Remove the Cloudera Manager agents (optional)

Only if you are also removing the hosts from Cloudera Manager entirely. Run this on each ECS host, then remove the hosts from the Cloudera Manager UI:

```text
[root@pvcecs-master ~]# systemctl stop cloudera-scm-agent
[root@pvcecs-master ~]# dnf remove -y cloudera-manager-agent cloudera-manager-daemons
[root@pvcecs-master ~]# rm -rvf /opt/cloudera/cm-agent/
[root@pvcecs-master ~]# rm -rf /opt/cloudera/ /var/lib/cloudera-scm-agent
```

### A scripted alternative

Alternatively, an experimental script is available. This script combines steps 3 through 5. The script is available here: [https://github.com/cloudera-labs/snippets/blob/main/private-cloud/kill-2-rke.sh](https://github.com/cloudera-labs/snippets/blob/main/private-cloud/kill-2-rke.sh)

### 7. Reboot and verify

Reboot the host(s). Before you install ECS again, ensure that the IP tables list is empty by executing the following command:

```text
[root@pvcecs-master ~]# iptables -L
```
